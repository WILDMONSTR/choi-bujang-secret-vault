# BYTE BACK 방어전 자료실 · 3단계

이 저장소는 3단계 학습용 구성입니다. 화면은 Vercel 서버 함수 `/api/notes`를 통해 Supabase의 `public.learning_notes` 테이블에서 가상 메모 네 건을 읽으며, 화면에 Supabase Auth 이메일·비밀번호 로그인과 로그아웃 UI를 제공합니다. 실제 사용자 자료나 실제 비밀값은 이 실습에 넣지 마세요.

## 3단계: Supabase Auth 로그인 UI

- `public/index.html`은 Supabase 공식 JavaScript SDK `@supabase/supabase-js` 2.117.2를 사용해 `signInWithPassword`, `signOut`, `onAuthStateChange` 흐름을 연결합니다. 로그인 후에는 계정 이메일과 로그아웃 버튼이 표시되고, 로그아웃하면 로그인 폼으로 돌아옵니다. 인증 오류의 이유는 화면에 표시합니다.
- 프로젝트 URL은 화면 코드에 설정되어 있습니다. `SUPABASE_PUBLISHABLE_KEY`의 교체용 값을 실제 Supabase `sb_publishable_...` 공개 키로 바꿔야 로그인할 수 있습니다. 키는 Supabase의 Project Settings → API Keys에서 확인하세요. `sb_secret_...` 서버 비밀 키는 브라우저에 넣지 마세요.
- **중요:** 이 단계는 로그인·로그아웃 UI를 붙인 단계입니다. `/api/notes`에는 여전히 로그인·호출자 인증 검사가 없으므로, 로그인하지 않아도 해당 API를 직접 호출할 수 있습니다. 현재 UI를 API 접근 제어 완료로 간주하지 마세요.

## Vercel 환경변수 설정

1. Vercel 대시보드에서 이 프로젝트를 열고 **Settings → Environment Variables**로 이동합니다.
2. `SUPABASE_URL`에 Supabase 프로젝트 URL을 설정합니다.
3. `SUPABASE_SECRET_KEY`에 Supabase의 secret API key를 설정합니다. Supabase 대시보드의 **Project Settings → API Keys**에서 확인할 수 있습니다.
4. 사용할 배포 환경(Production, Preview 등)을 선택해 저장하고, 새 배포를 실행합니다.

환경변수의 **이름과 용도만** 코드에 적습니다. 실제 값은 Vercel의 환경변수 입력란에만 입력하세요. 키를 채팅, GitHub, 브라우저 코드, URL, 응답 본문 또는 로그에 넣지 마세요. 이 키에 `NEXT_PUBLIC_`이나 `VITE_` 같은 브라우저 노출용 접두사를 붙이지 마세요. 실제 키를 나에게 보내지 않아도 됩니다.

## API와 알려진 약점

- `api/notes.js`는 서버에서 `SUPABASE_URL`과 `SUPABASE_SECRET_KEY`를 읽어 `learning_notes` 테이블의 `title`과 `content`만 조회합니다.
- 함수는 정해진 네 제목에 해당하는 가상 메모만 응답하며, 키와 원본 오류는 응답하거나 로그로 남기지 않습니다.
- Supabase secret key는 RLS를 우회할 수 있는 높은 권한의 키이므로 서버 밖으로 유출되면 안 됩니다.
- **현재 알려진 약점:** `/api/notes`는 공개 URL이고 호출자 인증·로그인 확인·요청 제한을 구현하지 않았습니다. 누구나 URL을 직접 열어 네 건의 가상 메모를 읽을 수 있습니다. 이 단계에서는 가상 데이터만 사용하며, 실제 자료를 다루려면 인증·인가·요청 제한을 추가해야 합니다.

## 정적 파일과 배포

- `public/data.json`은 제거했습니다. 빌드 스크립트도 예전 파일이 남아 있으면 지우며 다시 만들지 않습니다. 배포 주소의 `/data.json`은 찾을 수 없음(일반적으로 HTTP 404)이 정상입니다.
- 화면은 `/api/notes`를 호출해 네 카드를 그립니다. 브라우저에는 공개 프로젝트 URL과 publishable key만 사용하며, 서버 전용 secret key는 포함하지 않습니다.
- Vercel 빌드는 `aleph.config.json`의 2~12단계를 지원합니다. 비로컬 배포에서는 기존처럼 `public/aleph.json`에 배포 식별 정보를 생성합니다. `--local` 빌드는 해당 배포 식별 파일을 생성하지 않습니다.
- `npm run build -- --local`은 로컬 빌드 확인용이고, 실제 Vercel 배포 완료를 증명하지 않습니다.
- 점검 명령은 `npm run test:r5`와 `npm run test:package`입니다. 실행하지 않은 테스트나 실제 API 요청을 성공했다고 간주하지 마세요.

### 2. GitHub 최신 실행 파일 검색

저장소를 로컬에 복제한 환경에서 PowerShell 또는 터미널로 다음 명령을 실행합니다. 먼저 원격 브랜치를 갱신한 다음, 현재 `origin/main`의 브라우저·서버 실행 파일과 빌드 스크립트만 검색합니다.

```sh
git fetch origin
git grep -n -F -e "실습용 가상 과제 기록" -e "실습용 가상 포트폴리오 기록" -e "실습용 가상 리추얼 기록" -e "실습용 가상 행정 기록" origin/main -- public api scripts src
```

- 일치 행이 출력되면 파일 경로와 줄 번호를 기록하고 해당 문장이 실행 파일에 포함된 이유를 확인합니다.
- 출력이 없고 종료 코드가 1이면 지정한 경로에서 정확한 문장을 찾지 못한 것입니다. 이는 해당 실행 파일 경로의 검색 결과일 뿐, 과거 커밋이나 이전 배포까지 검색한 결과는 아닙니다.
- 이 README에는 검색어 자체가 적혀 있으므로 위 명령은 README를 포함하지 않는 실행 파일 경로만 대상으로 합니다. README의 검색어 일치 결과를 메모 본문 유출로 세지 마세요.

GitHub 웹에서는 저장소의 `main` 브랜치에서 **Code** 검색을 사용해도 됩니다. 단, 검색 인덱스나 검색 범위에 따라 결과가 달라질 수 있으므로 중요한 판정은 최신 브랜치의 파일 내용을 직접 확인하거나 위 명령으로 재검증합니다.
